# Implicit state machine inventory

Static audit of the native Android app on 2026-11-07. **75 workflow/state-machine boundaries identified**, including one debug-only simulation boundary. Boundaries overlap where a larger machine contains smaller machines. This is a count of useful review boundaries, not a count of independent finite automata.

Here, an implicit state machine means that an event changes what actions are legal next, but the phase is reconstructed from nullable fields, flags, collections, timestamps, filesystem state, coroutine ownership, or control flow. A named status enum does not make a machine fully explicit when other fields determine its legal transitions.

Scope: production Kotlin under `android/app/src/main/java`, embedded reader/browser JavaScript, and the debug simulation lifecycle. Searches covered mutable fields, atomic/deferred/job ownership, status writes, state flows, callbacks, timers, recovery markers, and named state types. This is a source inventory, not runtime verification or proof that every possible execution path has been enumerated. Ordinary form values, filters, expand/collapse toggles, parsing cursors, and caches with no meaningful workflow were excluded.

## Where I would start

1. **TTS session/output/service coordination.** Playback intent, actual output, initialization, persisted resume state, and audio focus all change independently. Model these as coordinated state components rather than one giant enum.
2. **Download execution and source recovery.** Separate job phase, retry schedule, source access, and permission to publish a result. Today, queue strings, timestamps, source circuits, and worker ownership jointly decide behavior.
3. **Full restore.** Keep the durable journal, and make the relationship between journal phases, filesystem observations, and rollback ownership explicit. Recovery must handle interruptions between any two writes/moves.
4. **AI queue handoff and result attention.** Job execution, persisted drafts, seen state, failure history, and dismissal are separate lifecycles. A terminal event does not by itself describe all of them.
5. **Activity startup and deferred external actions.** Intent precedence, source retries, and update installation depend on readiness and lifecycle events arriving in different orders.

These priorities describe architectural complexity and consequences of mistakes. They are not claims of demonstrated defects. A small, well-contained implicit machine can be perfectly adequate.

## Refactoring guidance

Start with ownership and events. For each boundary, write down its current state, accepted events, legal transitions, side effects, and recovery behavior. Replace strings that double as busy flags before replacing harmless local toggles. Keep progress text outside the phase model.

Use sealed states where phases require different data, such as a range selection waiting for its second endpoint. Use separate state components for independent concerns, such as playback intent and audio focus. Preserve generation checks for stale asynchronous results even after introducing typed states.

For tests, prioritize competing events: pause during preparation, cancellation during queue handoff, verification during a blocked download, restore during an in-flight commit, and process death between filesystem moves. These require transition/invariant tests, not just tests of enum values.
