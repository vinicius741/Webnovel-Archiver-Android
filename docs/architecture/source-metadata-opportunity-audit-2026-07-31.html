Source Metadata Opportunity Audit

The current app is not limited by the absence of Patreon or a numeric score. Each source publishes a different kind of reader signal: Royal Road exposes followers and favorites, Scribble Hub exposes a complete statistics page, SpaceBattles exposes forum engagement, and FanFiction.net exposes a compact story profile with reviews, favorites, follows, words, dates, and content classification. This report inventories the useful fields that are currently missing and gives a source-specific retrieval plan for a future implementation agent.

Executive recommendation

Implement one “Source statistics” block with native labels, backed by nullable typed fields. Do not turn every source into a fake five-star score. The most useful parity comes from showing each site’s own evidence of audience, size, recency, and classification.

The first implementation tranche should prioritize word/page size, audience counts, engagement counts, published/updated dates, and typed content labels. These are public, understandable to users, and available during the existing sync flow. Rankings, recent-reader lists, per-chapter favorites, and author achievement badges should remain out of the first version because they are volatile, privacy-sensitive, or expensive to normalize.

What the app captures today

The registry currently contains four providers in SourceRegistry. NovelMetadata has title, author, cover, description, tags, score, canonical URL, Patreon URL, and publication status. Story stores those values alongside locally derived chapter/download state. Tags are already displayed and filterable, but source-specific classification is flattened into one list. Score is a nullable display string, and Patreon metrics only exist when a Patreon link is found.

Royal Road

Highest-value opportunity: expose the public fiction statistics block P0

Royal Road has no need for a Patreon link to provide useful audience data. A live fiction page publishes Overall Score, Total Views, Average Views, Followers, Favorites, Ratings, and Pages in one statistics block. The current provider already locates the score in the neighboring-label pattern, so the other fields can be added with the same label-driven parser.

Current code: RoyalRoadProvider.parseMetadata. Retrieval: the already fetched fiction page; no additional request is needed.

Scribble Hub

Highest-value opportunity: fetch the linked statistics page P0

Scribble Hub is the richest source for measurable story metadata. Its statistics route exposes a compact header and a details block with total views, chapter views, average views, word count, average words, pages, favorites, chapters/week, readers, rating count, rating distribution, and reviews. The base series page remains the right place for title, description, tags, status, and the chapter list; statistics should be fetched from the canonical series URL plus /stats/.

Current code already has Cloudflare-aware source transport. The stats page should use the same NetworkClient, source request gate, cookies, retry policy, and cache behavior as the base series page.

SpaceBattles

Highest-value opportunity: use forum engagement as the source’s score equivalent P0

SpaceBattles stories are forum threads rather than rating-first fiction pages. The useful metadata is therefore community activity: watchers, replies, views, likes, and awards, plus words. These metrics are visible in the SpaceBattles Story Library and are the natural replacement for a missing rating or Patreon number.

Current code already fetches the main threadmarks page and parses .threadmarkListingHeader-stats dl for status. The same label/value parser can capture words there. The library engagement block may require a second source page or a stable thread-specific library lookup; verify the live HTML with a fixture before implementation because SpaceBattles has recently changed its XenForo layout.

Cross-source model recommendation

Use a small common typed model for stable numeric fields, plus typed classification fields. Keep native names where the semantics differ. Do not put every source-specific value into a single unstructured string map: that would be quick to add but would make sorting, trend history, and accessibility harder later.

Suggested nullable shape

data class SourceStats(
    val views: Long? = null,
    val chapterViews: Long? = null,
    val averageViews: Long? = null,
    val followers: Long? = null,
    val readers: Long? = null,
    val watchers: Long? = null,
    val follows: Long? = null,
    val favorites: Long? = null,
    val ratingsCount: Long? = null,
    val reviewCount: Long? = null,
    val replyCount: Long? = null,
    val likes: Long? = null,
    val awards: Int? = null,
    val wordCount: Long? = null,
    val wordCountIsEstimated: Boolean = false,
    val averageWords: Long? = null,
    val pageCount: Long? = null,
    val chaptersPerWeek: Double? = null,
    val publishedAt: Long? = null,
    val updatedAt: Long? = null,
)

This is a recommendation, not an instruction to change code in this audit. The nullable design matters: an absent metric means “the source did not publish or the parser did not obtain it,” not zero. If source-specific names become too wide for Story, keep the same shape under a nested sourceStats property.

Do not normalize away the labels. A future UI can show Followers, Readers, Watchers, and Follows as separate rows while still using one typed model. That makes the result honest and makes it obvious to users why two sources expose different numbers.

Implementation roadmap for a future agent

1. Extend metadata models P0

Add nullable sourceStats and typed classification fields to NovelMetadata and Story. Preserve existing JSON defaults so old libraries restore cleanly. Keep score and generic tags for compatibility.

2. Parse one fixture per source P0

Expand the existing source fixture tests with statistics and classification examples. Use label-driven parsers and numeric normalization, not positional child indexes or one giant regex.

3. Fetch only one extra page P0

Royal Road, SpaceBattles, and FanFiction.net can use their existing story/thread response. Scribble Hub needs a canonical /stats/ request. Reuse source pacing, Cloudflare cookies, and network error classification.

4. Add a source-stat card P0

Show 4–6 high-value values on Details with the source’s native labels; show the full breakdown in an expandable/details area. Hide absent metrics and never render missing ratings as zero.

5. Add snapshot history later P1

The existing StoryMetricSnapshot design already calls for nullable future fields. Add views/followers/readers/watchers/favorites/words only after current values render correctly. Trend monotonic audience counters cautiously because source corrections and resets happen.

6. Defer volatile fields P2

Do not block the first release on rankings, per-chapter favorites, recent readers, author achievements, review bodies, or source search pages. They add traffic and churn without improving the basic novel card proportionally.

Parsing guardrails

  • Match visible labels such as Followers, Words, or Reviews after whitespace normalization. Do not rely on the current order of a statistics list.
  • Parse abbreviations such as 2K or 2.36M into numeric snapshots while retaining a formatter for user-facing compact display.
  • Keep source-reported zeros distinct from missing values. A page with “0 ratings” has data; a page where the block is absent does not.
  • Keep counters and classifications source-scoped. “Replies” is not “reviews,” and FanFiction.net’s T is not a score.
  • Update StoryMetricSnapshot with nullable fields only, following the compatibility guidance in docs/architecture/metric-trends.md.
  • Do not add a second AppStorage owner or a separate metadata write path. The existing sync/repository flow remains the persistence boundary.
