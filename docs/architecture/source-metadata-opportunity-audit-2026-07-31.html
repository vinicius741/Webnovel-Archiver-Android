Source Metadata Opportunity Audit

Each source publishes a different kind of reader signal, but availability is not a reason to put every signal in the app. This report keeps the full opportunity inventory, then applies a product rule: show at most four source-native facts on Details, add no new rows to library cards, and never invent a score for a source that does not publish one.

Executive recommendation

Use source-specific metadata, but give every source the same display budget. Show no more than four curated facts on Details. Royal Road and Scribble Hub keep their real score in the existing header row, extended with rating count, and get at most three cells in a compact “At the source” block. SpaceBattles and FanFiction.net have no score row and may use up to four native facts. Different labels are a feature because they tell the truth about what each number means.

The first implementation should answer four useful questions without becoming a dashboard: How well received is it? How large is its audience? How much is there to read? How recently has it moved? A source does not need an answer in every category. Hide missing categories instead of filling them with weaker metrics or zeroes.

Do not show the complete inventory, even behind an expanded panel in the first release. Fields outside the shortlist may still be parsed later for filtering, status accuracy, or future features, but should earn a concrete use before entering the UI or snapshot history.

What the app captures today

The registry currently contains four providers in SourceRegistry. NovelMetadata has title, author, cover, description, tags, score, canonical URL, Patreon URL, and publication status. Story stores those values alongside locally derived chapter/download state. Tags are already displayed and filterable, but source-specific classification is flattened into one list. Score is a nullable display string, and Patreon metrics only exist when a Patreon link is found.

Recommended display shortlist

One contract, different source facts

  • Library cards: keep the current source, publication status, real score when available, Patreon summary, and tags. Do not put views, followers, likes, reviews, or word count on the card. A card without a score is not incomplete.
  • Details: allow a maximum of four source facts across the whole header/stat area. Extend the existing score row with its rating count; count that pair as one fact. The separate “At the source” block therefore has at most three cells for a scored source or four for an unscored source. Hide it when nothing reliable was obtained.
  • Activity: integrate the source-updated date with publication status instead of spending a statistics tile on it. Do not confuse it with the app’s local sync time.
  • Classification: keep genres, fandoms, and characters in the existing tag/filter experience. Content rating and warnings are the only classification fields important enough to receive distinct treatment; show language only when it is not the app/user default.
  • More data: use the existing “open source” action for the exhaustive source view. The app should not reproduce each website’s analytics page.

Answer to the parity question: aim for parity of usefulness and visual weight, not parity of field names. A SpaceBattles story with “842 watchers” and a Royal Road story with “4.6 from 1,240 ratings” can occupy the same amount of space without pretending those figures are comparable.

Scribble Hub

Highest-value opportunity: fetch the linked statistics page P0

Scribble Hub is the richest source for measurable story metadata. Its statistics route exposes a compact header and a details block with total views, chapter views, average views, word count, average words, pages, favorites, chapters/week, readers, rating count, rating distribution, and reviews. The base series page remains the right place for title, description, tags, status, and the chapter list; statistics should be fetched from the canonical series URL plus /stats/.

Current code already has Cloudflare-aware source transport. The stats page should use the same NetworkClient, source request gate, cookies, retry policy, and cache behavior as the base series page.

Highest-value opportunity: show forum-native engagement without calling it a score P0

SpaceBattles stories are forum threads rather than rating-first fiction pages. Watchers and likes can still help a reader understand audience intent and reaction, while words describes size. They should occupy the same visual space as other sources’ facts, but they are not a replacement value that can be compared with a rating.

Current code already fetches the main threadmarks page and parses .threadmarkListingHeader-stats dl for status. The same label/value parser can capture words there. The library engagement block may require a second source page or a stable thread-specific library lookup; verify the live HTML with a fixture before implementation because SpaceBattles has recently changed its XenForo layout.

Cross-source model recommendation

Use a compact typed metric collection plus typed classification fields. Keep native meanings in an enum and map each kind to its source label. This avoids both a loose string map and a wide data class with a nullable property for every fact any source might ever publish. Most importantly, keep display selection outside the persisted model: obtaining a metric does not automatically grant it screen space.

Suggested persisted shape

enum class SourceMetricKind {
    TOTAL_VIEWS, FOLLOWERS, READERS, WATCHERS, FOLLOWS,
    FAVORITES, RATINGS, REVIEWS, LIKES, WORDS, PAGES,
}

data class SourceMetric(
    val kind: SourceMetricKind,
    val value: Long,
    val isEstimated: Boolean = false,
)

data class SourceMetadata(
    val metrics: MutableList<SourceMetric> = mutableListOf(),
    val publishedAt: Long? = null,
    val updatedAt: Long? = null,
    val contentRating: String? = null,
    val contentWarnings: MutableList<String> = mutableListOf(),
)

This is a recommendation, not an instruction to change production code in this audit. An absent metric means “the source did not publish or the parser did not obtain it,” while a present metric may legitimately have value zero. Keep the existing score for compatibility and treat RATINGS as its confidence context.

Display policy is separate from storage. A source-specific policy should select the ordered metric kinds listed in the shortlist and cap the result at four. The UI then renders native labels such as Followers, Readers, Watchers, and Follows. Adding another parsed enum value must not make another cell appear automatically.

Implementation roadmap for a future agent

1. Extend metadata models P0

Add a default-empty typed sourceMetadata collection to NovelMetadata and Story. Preserve existing JSON defaults so old libraries restore cleanly. Keep score and generic tags for compatibility.

2. Parse one fixture per source P0

Expand the existing source fixture tests with statistics and classification examples. Use label-driven parsers and numeric normalization, not positional child indexes or one giant regex.

3. Keep retrieval proportional P0

Royal Road and FanFiction.net can use their existing story response. Scribble Hub justifies one canonical /stats/ request. SpaceBattles must prove a stable story-specific library lookup before adding its extra engagement request; Words and source-updated already come from existing paths. Reuse source pacing, cookies, and network error classification.

4. Add one source-stat block P0

Extend the existing Details score row with rating count, then show at most three additional facts for scored sources or four for unscored sources. Use native labels and a compact grid that collapses cleanly for two or three cells. Do not add a full expandable analytics panel or change library cards.

5. Add snapshot history later P1

The existing StoryMetricSnapshot design already supports nullable future fields. Add trends only after users have a reason to revisit a metric over time; a value being available does not by itself justify a chart. Treat source corrections and counter resets carefully.

6. Defer volatile fields P2

Do not block the first release on rankings, per-chapter favorites, recent readers, author achievements, review bodies, or source search pages. They add traffic and churn without improving the basic novel card proportionally.

Parsing guardrails

  • Match visible labels such as Followers, Words, or Reviews after whitespace normalization. Do not rely on the current order of a statistics list.
  • Parse abbreviations such as 2K or 2.36M into numeric persisted values while retaining a formatter for user-facing compact display.
  • Keep source-reported zeros distinct from missing values. A page with “0 ratings” has data; a page where the block is absent does not.
  • Keep counters and classifications source-scoped. “Replies” is not “reviews,” and FanFiction.net’s T is not a score.
  • If a shortlisted metric later earns trend history, update StoryMetricSnapshot compatibly and follow docs/architecture/metric-trends.md. Do not snapshot the complete inventory by default.
  • Do not add a second AppStorage owner or a separate metadata write path. The existing sync/repository flow remains the persistence boundary.
