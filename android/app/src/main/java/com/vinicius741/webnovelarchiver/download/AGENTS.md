# Downloads

Applies to `download/` (engine, scheduler, foreground service) and `feature/downloads/` (the global queue screen). A download job's lifecycle fields are owned by `domain/download/DownloadJobTransitions.kt`; see `domain/AGENTS.md`. These rules add to `android/AGENTS.md`.

- "The download screen" is ambiguous: `feature/downloads/QueueScreen.kt` (`showQueue`) is the global queue across all stories; `feature/details/DetailsScreenDownload.kt` is the per-story download banner on the details page. The top-level `download/` package is the engine/planning layer (`DownloadEngine`, `DownloadForegroundService`, scheduler) and contains no screen — confirm which surface a change targets before editing.
- The Downloads screen lists novels in real download order: the scheduler takes pending jobs first-in-first-out per site, so queue list position *is* priority. `download/DownloadQueueSectionPlanning` splits the queue into Needs attention (one card per Cloudflare-blocked site, plus retryable failures), Downloading now, Up next, Paused, and a folded Finished section; `DownloadQueueOrderPlanning` rewrites list order for drag-to-reorder, "Download now" (also a drop onto the Downloading now card), and "Move to bottom"; `DownloadQueueStatusCopy` owns the plain-language status lines. `feature/downloads/QueueItems.kt` flattens the plan into rows (chapter rows are separate items so countdown ticks rebind one row).

## The Downloads screen (`feature/downloads/`)

- `QueueScreenModel` (kept in `ScreenModelStore` under `AppRoute.Queue`, so it lives while Downloads is in the history) owns the screen's state: it combines the repository's published `downloadState` (never deep-copied), the request pacer's snapshots, `SourceCheckOutcomes`, a one-second ticker and the user's expand/collapse choices (novels and the Finished section) into `QueueUiState` (rows, subtitle, app-bar plan). It follows those sources only while a renderer collects, plans off the main thread, and skips a tick when nothing a row shows can change (no queue, check, blocked-site or choice change and no countdown running). After a drag it holds the dragged order until the saved queue arrives (or 3 s). Expand choices reset when Downloads leaves the history.
- Every queue change is a `QueueControl` run through `QueueScreenModel.run`, which applies it through `QueueData` (`HostQueueData` maps it to `DownloadEngine`), keeps it alive if the screen goes away mid-save, starts the download service for resume/retry, and reports a failed save through `messages`. "Download now", a drop onto Downloading now, "Move to bottom" and reordering are controls too; Verify opens `CloudflareSolveActivity` through `QueueData.startSourceCheck`.
- `QueueScreen.kt` is the renderer: it rebuilds only when the app bar's actions change and otherwise submits rows to `QueueListAdapter` (DiffUtil over immutable rows, list position through `rememberListPosition`) and patches the subtitle. `QueueListAdapter` keeps an `ItemTouchHelper` limited to collapsed Up next cards, which may drop among Up next or onto Downloading now. `QueueMenus` holds the app-bar, novel, chapter and site-check menus; they read the queue from the model at tap time and call model actions. Renderer and menus never call the engine or repository.
- A passed check in `CloudflareSolveActivity` calls `resumeDownloadsAfterSourceCheck`, which requeues that site's blocked chapters without spending retries; `SourceCheckOutcomes` (in-memory) drives the card's Verified / Still blocked states.
