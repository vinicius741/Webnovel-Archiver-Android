# AI

Applies to `ai/` and `feature/ai/`. See also `docs/ai/`. These rules add to `android/AGENTS.md`.

- `source/` owns network/source providers and Cloudflare detection/solving; `sync/`, `download/`, `epub/`, `cleanup/`, `tts/`, and `ai/` own their respective engines and planning logic. The `ai/` package contains the OpenRouter generation and decision-model layers (client on a plain OkHttp stack — deliberately not the Cloudflare-intercepted `NetworkClient` — plus description and cover-art planning/engines); cover generation runs as a process-lifetime background job (`AiCoverJobCoordinator`, a thin wrapper over the generic `AiJobCoordinator`, kept alive by `AiJobForegroundService`), persisting each result before announcing it. The former Chapter polish (rewrite/verifier) feature was removed in October 2026: startup deletes its leftover `chapter_rewrites/` tree, and full-backup restore still validates but discards that tree from older backups. The per-novel AI UI is `feature/ai/AiControlsScreen.kt` (the story page's AI tab; tapping a cover opens the full-screen `showCoverViewer` to compare and choose), which saves cover experiments locally and changes the displayed cover only when the user chooses "Use this cover" in the full-screen viewer (opened from its cover strip) or taps Use new cover — see `docs/ai/`. The AI screen's Characters tab (`feature/ai/AiCharactersTab.kt`, `AiCharacterPage.kt`) runs on its own process-wide `CharacterJobCoordinator` (also kept alive by `AiJobForegroundService`): `CharacterEngine` counts names on the device (`CharacterMining`), makes one text-model call for the list (`CharacterRosterPlanning`), and paints portraits from a per-character decision scan (`CharacterAppearanceRubric`; the lead reuses the cover scan). The list and portraits live in `CharacterStore` (`ai_characters/<story>/`, device-local, not in backups, deleted with the novel); see `docs/ai/ai-characters.md`.
- Automatic cover and description context use one `ChapterEvidenceSelector` and `DecisionClient` to score downloaded passages with the user-chosen OpenRouter decision model (`AiSettings.decisionModel`, default Jev) through the shared `OpenRouterClient` and device-local OpenRouter key. Each generator supplies an `EvidenceRubric` — `CoverEvidencePlanning` (visual evidence over whole-chapter passages: first 10 chapters then a book-spanning scan with a 60-chapter floor, per-passage main-character-appearance Nouls whose flagged passages reach the prompt writer verbatim, plus chapter-level `age_shown`/`life_stage` questions that `CoverPhasePlanning` turns into story phases so the cover paints one phase (default the main one, `Story.aiCoverPhase` overrides; scoping lives in `CoverEvidenceSelection.kt`); requests stay under ~30 KB to avoid OpenRouter's long-context switch) and `DescriptionEvidencePlanning` (premise without spoilers, opening chapters in reading order) — while `ChapterEvidencePlanning` owns sampling, scan orders and the final choice. Changing a rubric's questions changes its cache keys and rescores. `ChapterEvidenceStore` stores disposable content-addressed score responses and the last automatic chapter selection per `EvidenceSelectionKind` (plus the last cover scan's story phases) under app cache, outside library/backup storage; never put source text or keys in it. Construct it during IO container setup so UI selection reads use its cached snapshot without disk access or cache-maintenance locks. Manual chapter selections bypass the scan. Text-model pickers list only text-output models (`OpenRouterClient.fetchModels` drops image/audio outputs); the decision picker uses `fetchDecisionModels`.
- **AI tab: model and renderer.** The AI tab runs on the screen-model pattern:
  - `AiControlsScreenModel` (one per story, from `aiControlsModel(storyId)`) publishes `AiControlsUiState`: the model's copy of the story, the open sub-tab, the open character page and the Supporting toggle, this story's AI slot (`StoryOperations.ai`), cover and character jobs, the results in `AiAttention`, the persisted `aiCoverUnseen`, the saved cover versions and the character list (both loaded by the model while their sub-tab is watched), settings, cost lines and the evidence cache's phases and selections. Every action (starting jobs, use/keep/delete/reuse covers, prompt box, context chapters, story phase, descriptions, portraits) is a model method; toasts come out of `messages`. Reads and writes go through `AiControlsData` and `AiControlsJobs` (`AiControlsRepositoryData.kt`; fake them in tests).
  - It is keyed by the AI route (`AppRoute.AiControls`), not the Overview key `StoryPageScreenModel` uses: the store holds one model per key and replaces a model of another type, and every tab of a story stays in the history together, so both models live exactly as long as the story's page. The sub-tab and character page therefore reset when the story leaves the history; the job chip and the hero's Review button open the tab they need.
  - While a renderer collects its state, the open sub-tab counts as looked at: its unseen marker, chip failure and dismissals are cleared, and an unseen cover is marked seen.
  - `showAiControls` builds the tab from that state and starts an `AiControlsRenderer`. A change of `AiControlsUiState.layoutKey()` re-renders the tab; progress messages patch their lines; the cover strip and character list fill their slots when they load (a changed list already on screen re-renders, keeping scroll). Typing in the prompt box keeps the `CoverPrompt` revision, so it never redraws the tab; a job, Clear or Reuse this prompt changes the revision and redraws the box.
  - Nothing outside the tab patches its views. To show something new, publish it (`AiAttention`, `StoryOperations`, the repository) or add it to the state.
- **`AiAttention`** (`AppContainer.aiAttention`, process-wide) holds what outlives the tab: description drafts (never persisted), the shown cover draft, the prompt box, unseen description/character markers, and the job chip's failures (oldest first) and dismissals. The app-wide job chip (`AiJobChip.kt`, attached once per activity like the TTS mini-player) observes it with the cover jobs, the AI slot and `aiCoverUnseen`, and hides on its own story's AI tab. The story page reads a waiting cover from it through `StoryPageUiState.coverToReview`.
- **Jobs.** Cover, description (`AiDescriptionJobCoordinator`) and character jobs run on process-wide coordinators. `app/AiJobUiBridge.kt` only mirrors running cover and description jobs into `StoryOperations.ai` (a job's terminal event also ends the slot, because the mirror can miss a job that fails at once), writes finished results and failures into `AiAttention`, and toasts (a failure toasts on that story's AI tab and goes to the chip elsewhere); it redraws nothing. `StoryOperations.ai` is separate from `.content` (sync / cleanup / EPUB): only `.content` gates the story page's content actions, and only `.ai` gates AI starts.
- Model pickers live in AI Settings. Their rows observe `AiModelFieldsModel` (keyed by the AI Settings route); picker callbacks call `refreshAiModelFields()`, which pokes that model, so a row rebuilt by a fold while the picker stayed open still refreshes. Model and reasoning edits stay in `AiModelSelectionDraft` until Use model commits both together.
