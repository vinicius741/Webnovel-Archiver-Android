# Generated narration

Applies to `narration/`, `feature/narration/` (the Listen destination), `feature/details/ChapterAudio.kt`, and the Rust server in `scripts/narration-server`. These rules add to `android/AGENTS.md`.

- `narration/` owns pre-generated chapter audio (see `docs/tts/narration-pregeneration-plan.md`). A chapter plays **only** from its complete pack: `TtsEngine.loadOutputLocked` is the single start point and gates on `NarrationCoordinator.readyPack` (matching text fingerprint), playing through `tts/PackTtsOutput` with no speech engine or model loaded; otherwise the session stays paused with `TtsPlaybackErrorKind.AudioNotGenerated` and the chapter is queued first. Audio made from text that has since changed (a cleanup rule, a re-download) still plays: `TtsPlaybackPreparer` prepares the pack's own `recipe.sentences` (same chunking version) instead of the current text, so its fingerprint matches. The Listening settings sample keeps the real-time rendered path, except a sample in a built-in model that is not on the phone: it generates on the chosen computers first (`NarrationSampleRenderer`, chips in the Try it card via `TtsSamplePlanning`) and never borrows a stand-in voice. `NarrationCoordinator` (one instance in `AppContainer`) owns `NarrationStore` (packs in `filesDir/narration/packs/<sha story>/<sha chapter>/`, immutable `v-<id>` version folders with `recipe.json`, per-sentence clips (AAC-LC 64k through `AacNarrationCodec` in the `NarrationClipFormat` layout with the measured codec delay stored per clip; reused clips are copied, never re-encoded; packs from before 2026-11-20 hold PCM `.pcm` clips that still play and `NarrationRecompressor` converts in the background while the generator is idle, publishing only if the pack is unchanged, pausing with growing waits after codec failures instead of stopping, and publishing its progress as `NarrationCoordinator.compression`, shown in Settings and Listen › Generated by `CompressionStatusView`; see `docs/tts/narration-audio-compression.md`), `index.json` written last and an atomically replaced `current` pointer; playback `retain`s its version; the startup sweep never deletes a published pack, and packs of stories no longer in the library show as detached), `NarrationQueue` (`queue.json`: jobs with the voice resolved at enqueue, pause, keep-ahead count, measured speed), `NarrationGenerator` (one worker; Kokoro converts directly to PCM without a temporary WAV; `KokoroRuntime.refitThreads` keeps the native thread count within the cores Android allows (`KokoroThreads.forNow`); yields at the next sentence when another job is moved first, keeping its clips; resumes at the first missing clip, reuses identical clips of the same voice, re-checks job, text fingerprint and `libraryGeneration` before publishing, pauses the queue when storage runs out) and keep-ahead (`NarrationPlanning.keepAheadChapters`: a fixed window after the playing chapter, add-only). Generation never substitutes another engine (`NarrationSynthesizers`). Built-in-model jobs (Kokoro v0.19, v1.0, Phonon; the server runs each installed model and is told which per request) can generate on the owner's computers (`NarrationQueueDocument.servers`/`generateOnIds`/`phoneFallback`; several chosen computers share each chapter's sentences through `NarrationPlacePool`, which sets aside one that fails or stops for memory, probes it back, waits up to 15 minutes while none can be reached (a Wi-Fi change) and pauses only after that or for a problem waiting cannot fix, unless the phone stands in; `NarrationServerClient` over a plain socket, `scripts/narration-server`; see `docs/tts/remote-narration-servers.md`). Each computer has a local-network and a Tailscale address; `reachServer` tries the local one first, and `NarrationServerMonitor` checks every 30 s, while Settings › Listening is visible, whether each computer is online (`/v1/status`, which neither loads the model nor keeps the computer awake; Setup shows it per computer): the remote synthesizer shares the phone's `KokoroVoices.voiceKey`, the generator keeps `parallelism` sentences unanswered, starts up to three per slot ahead of the one being written so a finished clip never holds a slot (`ClipsAhead`), and writes clips in order, a place change switches at the next sentence, and a `NarrationServerProblem` from the pool pauses the queue (`pausedForServer`) instead of failing jobs. The client keeps connections alive; a `503` (the server short of memory) is `NarrationServerBusy`, which the pool waits out (`Retry-After`) on that computer while others keep generating, and `NarrationProgress.waitingFor` explains the wait when none can. The server is Rust and runs on both of the owner's computers, the Bazzite handheld (systemd user unit) and the MacBook (launchd agent): `cargo test` in `scripts/narration-server`; build needs `SHERPA_ONNX_LIB_DIR`, which `setup.sh` provides; a change to it must keep both systems working (the macOS notes are in `docs/tts/remote-narration-servers.md`). `NarrationForegroundService` (`specialUse`, wake lock leases) keeps the process alive while runnable jobs exist; the worker waits until this service enters the foreground and suspends between clips if the service stops. A refused background start leaves jobs queued. Queue deduplication skips only packs matching the current text and chunking version, so outdated audio can be generated again; screen statuses key cached text fingerprints by the chapter file's size and modification time, download time, cleanup rules and chunking version, while playback always checks the text it prepared. Publication and job removal share the queue lock so cancellation or a voice replacement cannot lose the newer request. Doze needs the battery-optimization exemption the Narration screen offers. UI: `feature/narration/` (`AppRoute.Narration` is the Listen destination: a Now playing / Continue listening card over Queue (the cross-story generation queue grouped by story, with reordering, Clear queue and the live `NarrationLiveStatus` banner driven by `NarrationScreenPlanning.banner`) and Generated (each story's audio, storage once, restore leftovers in one row)); where audio generates (Generate on, computers) and the keep-ahead "Chapters ahead" stepper live in Settings › Listening (`feature/settings/SettingsTts.kt` hosts `setupSection`). A chapter's audio lives on the story page's Chapters tab (`feature/details/ChapterAudio.kt`: row labels from the queue and published packs, an Audio filter, long-press actions, the story audio menu); Select (`ChapterSelectionScreen`) is one selection for Download / Generate audio / Delete audio. The former Audio tab route (`narration_story`) decodes to the Chapters tab. Every "listen" entry point goes through `playIfGenerated`, which plays generated audio or queues the chapter at the front and starts it once ready; `playChapter` plays the tapped chapter itself (from the saved place only when that place is in it). The story page's Listen button uses `continueListening`, which resumes the story's listening place (never the bookmark's chapter unless the story has no place). All three run in `operations/ListenStarts` (one in `AppContainer`, one pending start at a time, a newer request replaces it); the `ScreenHost` functions of those names only pass it the activity's side (`ListenStartUi`: toasts, the permission prompt, waiting for the foreground, the playback service). Any start away from the saved place adds that place to the listening history first (`TtsPositionPlanning.historyForStart`), so it is never silently lost. Pure rules live in `NarrationPlanning` and `feature/narration/NarrationScreenPlanning` with JUnit tests. Generation speed and ETA use wall time; `narration_published` records audio/generation/render milliseconds, native inference threads, allowed CPUs and process importance.

## The Listen screen

- `ListenScreenModel` (keyed by `AppRoute.Narration`) owns the screen's state. It combines the coordinator's queue, progress, `generationRunning`, packs revision and compression with `TtsEngine.playbackState`, reading them through the fakeable `ListenData` (`RepositoryListenData`), and only while a renderer collects. It runs the queue changes off the main thread to completion (`NonCancellable`) and reports failures through `messages`. Play and resume go through `PlaybackControls`.
- `ListenUiState.content` (`ListenContent`) is what a build needs: queue cards with their stories and chapter titles, the generated audio split, storage, and whether to offer Generate on. A new instance comes only when its `ListenBuildKey` changes: the queue without its live-only fields (keep-ahead, speed measurements), the packs revision, or the running job. Its renderer (`ListenRenderer` in `NarrationScreen.kt`) rebuilds the screen when the key changes. On every other update it patches the banner (`NarrationLiveStatus`), the running job's row (`RunningJobRow`), the top card (`ListenNowCard`, bound from `ListenNow`) and `CompressionStatusView` in place, so progress ticks never rebuild.
- The saved place for the Continue listening card is looked up again on a stop and on each rebuild key change, and new models start from the last one found (`RepositoryPlayerData.lastContinuePlace`). The selected section and per-section scroll are renderer view memory that outlives the model.
